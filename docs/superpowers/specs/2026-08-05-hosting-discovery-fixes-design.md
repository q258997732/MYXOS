# 设备托管发现修复设计

## 目标

修复设备托管页面的 IP 范围发现、逻辑删除设备重新发现和逐 IP 结果表格筛选问题；整理安卓实例资源与卡顿诊断的后续实现依据，但不在本次实现中调用或新增设备诊断接口。

## 范围

- IP 范围模式支持将一个不规则 IPv4 范围转换为多个 CIDR，并逐个提交发现任务。
- 保持单次范围最多 256 个地址与端口范围校验，任一子任务提交失败时向用户明确展示失败原因。
- 新增 Flyway 迁移，移除 `device` 表遗留的原始 `(ip, port)` 唯一索引，继续使用仅对未删除记录生效的唯一约束。
- 在发现任务详情的逐 IP 结果表格中，为 IP、端口、结果、说明提供列头筛选；筛选在前端本地执行。
- 增加覆盖范围拆分、逻辑删除设备重新发现和逐 IP 筛选行为的测试。

## 不在范围内

- 不修改发现任务的数据模型、API 请求结构或扫描器的并发模型。
- 不将多个 CIDR 合并为一个任务，也不突破 256 地址限制。
- 不调用 MYTOS 设备接口，不新增安卓实例 CPU、内存、进程或卡顿监控功能。

## 根因

1. 前端 `ipRangeToCidr` 可以将任意范围拆分为 CIDR，但 `HostingView` 在结果超过一个 CIDR 时直接报错，因此 `192.168.107.1-192.168.107.254` 无法提交。
2. 初始迁移 `V1__init.sql` 建立了 `uk_ip_port (ip, port)`；后续 `V4__device_unique_index.sql` 只新增了基于 `deleted` 的有效记录唯一索引，未删除旧索引。逻辑删除记录仍会触发旧唯一约束，扫描器将其标记为重复。
3. 逐 IP 结果表格仅渲染 `taskDetail.ipResults`，未配置 Element Plus 的列筛选数据、筛选方法或动态筛选选项。

## 方案

### 范围发现

保留后端只接受一个 CIDR 的契约。前端根据 `ipRangeToCidr` 结果按顺序调用现有 `/api/discover/scan`；所有成功后显示已创建的任务数，任一失败则停止后续提交并显示已提交数量与错误信息。这样不引入新的批量 API 或后端事务语义。

### 逻辑删除重发现

新增版本号高于现有迁移的 Flyway 脚本，条件删除旧 `uk_ip_port` 索引。`uk_device_ip_port_active (ip, port, active)` 保留：有效设备必须唯一，逻辑删除设备的 `active` 为 `NULL`，扫描器插入新有效设备时不再冲突。扫描器现有的插入与 `DuplicateKeyException` 分支无需改动。

### 逐 IP 表头筛选

在发现详情抽屉中从当前 `ipResults` 动态派生筛选项。IP、端口、结果使用 Element Plus `filters` 与 `filter-method`；说明列使用用户输入的表头筛选文本并应用到本地展示数据。筛选不改变原始结果、统计数量或后端数据。

## 测试与验证

- 前端单元测试验证 `192.168.107.1-192.168.107.254` 会产出多个 CIDR 并按顺序调用发现 API。
- 前端单元测试验证四列筛选只显示符合条件的行。
- Flyway 集成或迁移结构测试验证旧唯一索引被移除、有效记录唯一索引仍存在，并允许同一 IP/端口在历史逻辑删除记录存在时插入新的有效记录。
- 执行现有 Maven 测试与前端构建；不向真实设备发起网络请求。

## 安卓实例后续诊断依据

MYTOS 当前没有实例实时 CPU、内存、进程或卡顿专用 API。后续应在采集服务实现固定只读 Shell 命令白名单：`/proc/stat`、`/proc/meminfo`、`top -b -n 1`、`dumpsys activity activities`、`dumpsys meminfo <package>` 与可选 `dumpsys gfxinfo <package> framestats`、PSI。卡顿状态应根据连续资源压力、慢帧、受控探针、boot status 与 ANR 线索组合判定，命令不可用或格式异常必须记录为 `UNKNOWN`。
